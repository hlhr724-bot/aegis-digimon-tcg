# TCG simulator bots and implications for Aegis training

Research date: 2026-10-15. Sources are project-owned documentation, implementation files, and research papers. This is a source review, not a benchmark of downloaded executables. Recommendations below are engineering inferences; they are not measured gains in Aegis.

## What exists

| Project                       | Evidence of a playable bot                                                                           | Coverage and qualification                                                                                                               | Useful lesson                                                                                                      |
| ----------------------------- | ---------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Digimon Project Drasil        | Python `BeelzemonXBot` implements mulligan, breeding, evolution, attack, and effect-order decisions. | A manual/tabletop simulator with partially automated bots, not a verified autonomous implementation of the complete game.                | Deck-specific ordered decisions can represent concrete strategy.                                                   |
| Magic: The Gathering Forge    | Rules engine with AI opponents and headless AI-versus-AI simulation.                                 | Broad playable simulator; its own documentation cautions that AI limitations remain and some matches become very slow.                   | Separate rules coverage from playing strength; retain batch results and diagnostics.                               |

## Digimon findings

Drasil is the closest inspected match to the requested game, but its bot guide requires the human to issue chat commands for effects affecting the bot's cards. Its repository describes a manual/tabletop simulator and lists bot reimplementation among upcoming work. This is useful prior art, not a replacement for Aegis's authoritative rules engine. [Project README](https://github.com/WE-Kaito/digimon-tcg-simulator), [bot guide](https://github.com/WE-Kaito/digimon-tcg-simulator/blob/ad1a4ecadf8e64ca7edec7ac2362444ec9d8cb75/Bot-Guide.md).

At inspected commit `ad1a4ecadf8e64ca7edec7ac2362444ec9d8cb75`, `BeelzemonXBot` contains explicit priorities for effect triggers and blockers, a rookie-based mulligan, and conditions around breeding, memory boosts, and trash thresholds. Its card factory registers 17 card identifiers and directly indexes that mapping. This supports describing it as a specific Beelzemon pilot; it does not support calling it a generic player for arbitrary legal decks. The AI README also describes development status and a known fifth-turn problem. [Pilot implementation](https://github.com/WE-Kaito/digimon-tcg-simulator/blob/ad1a4ecadf8e64ca7edec7ac2362444ec9d8cb75/ai/BeelzemonXBot.py), [card factory](https://github.com/WE-Kaito/digimon-tcg-simulator/blob/ad1a4ecadf8e64ca7edec7ac2362444ec9d8cb75/ai/card/CardFactory.py), [AI README](https://github.com/WE-Kaito/digimon-tcg-simulator/blob/ad1a4ecadf8e64ca7edec7ac2362444ec9d8cb75/ai/README.md).

## Training evidence

The EVA Hearthstone work optimizes 21 parameters of a greedy action evaluator through competitive coevolution. Its submitted agent placed second among 33 entrants in the 2018 premade-deck competition. The experiment used three particular decks; it is evidence that tuned interpretable policies can be effective, not that one evaluator masters all cards. Parents and offspring were reevaluated against each other, which the authors use to reduce noisy survival and expose agents to different behavior. This is a strong fit for the existing GEPA heuristic objective and archived opponents, without requiring a large neural network. [EVA paper, sections 3–5](https://arxiv.org/html/2410.19681v1).

The ByteRL exploitability study trained an approximate response in Legends of Code and Magic. Behavior cloning helped later reinforcement learning, but the experiment depended on ByteRL for deck drafting and restricted deck pools; it did not solve full Hearthstone or Digimon. The cloning dataset contained approximately 3.5 million state-action pairs from over 125,000 games. This is not a ready-made low-compute recipe for Aegis. The relevant lesson is that defeating one strong opponent can reflect exploitation of that opponent, rather than broad game competence. [ByteRL exploitability paper, sections 4–6](https://arxiv.org/html/2404.16689v1).

WindBot's executor interface and deck classes provide a concrete separation between reusable decision defaults and specialized deck behavior. This supports the existing generic-player-then-pilots direction; adapting a deck list alone is insufficient. [Executor implementation](https://github.com/IceYGO/windbot/blob/master/Game/AI/Executor.cs), [deck implementations](https://github.com/IceYGO/windbot/tree/master/Game/AI/Decks).

Magarena's MCTS documentation describes random rollouts, UCT, and selection by root visit count. It lists root parallelization and evaluation cutoffs under unimplemented extensions. Cutoffs could reduce simulation cost, but adopting one changes the teacher's evaluation and requires a separate strength comparison. They must not be reported as optimizations already proven by that implementation. [Magarena MCTS documentation](https://github.com/magarena/magarena/wiki/AIMonteCarloTreeSearch).

## Recommended adjustments under 4 GiB

These are proposed adaptations, not claims about what the cited projects prescribe verbatim. The exact batch sizes require local measurement.

1. **Make reflection batches small and paired.** Start a new, explicitly versioned training configuration with two to four complete seed/deck pairs per reflection batch. Include both learner seats and evaluate parent and candidate on identical tasks. Sample whole pair blocks instead of individual games. This reduces the amount of expensive feedback needed per proposal and avoids accidental seat imbalance. Keep the full validation set separate. It does not remove the initial validation cost imposed by the optimizer.
2. **Preserve the strong reference.** Keep the frozen 128-simulation MCTS reference and final held-out promotion criteria. A cheaper training-only opponent schedule can improve iteration speed, but its results must remain separate from strong-reference evidence. The existing adaptive ladder is already relevant infrastructure; reenabling it is a configuration change, not a newly invented algorithm.
3. **Extend diversity to generic training.** If the generic phase currently sees only MCTS, add a small frozen set of distinct heuristic opponents or archived generic candidates to training and diagnostic evaluation. Retain an explicit MCTS component so improving against cheap opponents cannot substitute for the user's objective. Do not claim that pilot archives already cover this generic-phase gap.
4. **Reuse expensive decisions as training evidence.** Collect player-visible observations, legal alternatives, selected actions, and terminal outcomes from training games only. Let GEPA inspect actionable mistakes and contrasting decisions rather than only aggregate win counts. Keep any imitation objective auxiliary: matching the teacher is not the same as beating it. Exclude validation and final-test trajectories from reflection.
5. **Measure throughput before adding search complexity.** Record per-game duration, per-search duration, completed simulations, decision count, memory peak, and queue state. Increase workers only after confirming the aggregate 4 GiB limit and CPU headroom. Larger memory allowance alone does not make single-threaded search faster. Keep valid deterministic caches, and never pool results across incompatible engine or opponent configurations.
6. **Turn validated pilot rules into guides.** Preserve the generic policy as a fallback and record the specialized rule changes that produced held-out gains. Publish their conditions and tradeoffs in English, with supported deck versions and evaluation scope. A guide should not imply that an untested combo or all matchups were learned.

## What would count as progress

A faster proposal cycle is useful only if the resulting policy retains validity and improves the strong-reference benchmark. Compare wall-clock time to the first reflected candidate, games per accepted improvement, paired held-out score differences, per-opponent regressions, and errors. Predeclare the comparison before a new campaign; do not change a running campaign's semantics while keeping its old provenance.

The existing random legal deck phase, pilot archives, separate final seed blocks, and strict final MCTS checks should be preserved. The most immediate incremental change is a configurable reflection batch made of complete pairs. Neither a small winning streak nor any of the external examples proves that a bot has learned the entire game or reached its best possible strength.

## Implemented adjustment

`evolve.py` now exposes `--reflection-pairs` with a default of four. Its custom GEPA sampler retains both seats and all archived opponents for each selected seed, visits every seed block within an epoch, and avoids padding the last batch with duplicate evidence. Campaign, stage, and runner fingerprints cover the setting and implementation. Integration tests use the installed GEPA API to verify that reflection receives paired training games while full validation and held-out evaluation remain unchanged.

The local migration preserves the existing frozen engine, 128-simulation reference, random-deck allocation, 24 selection pairs, and 100 final pairs. It starts a distinct run after in-flight games are saved, with three evaluator workers under the aggregate 4 GiB no-swap container limit. Exact-input cached games can be reused; repeated records never add independent samples. A higher worker count is an operational throughput hypothesis, not a measured speedup or strength claim.

Generic opponent diversity and teacher-decision reuse remain follow-up experiments. They have not been silently enabled by this adjustment. The initial validation cost also remains; the shorter batch applies to subsequent reflection cycles.
