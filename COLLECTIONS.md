# Persistent data inventory

Aegis persists application data in PostgreSQL. This filename names the inventory;
it does not imply a MongoDB collection layer. The API owns every query and write.
The authoritative schema is the ordered [migration registry](apps/api/src/db/migrations/index.ts),
currently migrations 001–052, plus the migrator's `schema_migrations` table.
Append migrations for released schema changes and update this inventory with them.

Tables below list their identity, important fields, and constraints. Foreign keys,
column defaults, full JSON payload shapes, and CHECK expressions are defined in the
linked migrations and domain owners; this document is not an executable schema.

## Other state boundaries

Colyseus rooms and the game engine hold live match state in one API process; it is
not a durable match database. Redis supports multiprocess coordination/presence
when configured. Card catalogs, effect snapshots, and the rules KB are repository
data, not PostgreSQL tables. Rollback input journals and private-state
fingerprints exist only inside an eligible live room and disappear with it.
Quick matchmaking stores each signed-in participant’s last public human opponent in
`aegis:quick-opponent:<accountId>` through the cluster presence, expiring after 30
minutes. Only started automatic public human matches write these keys. A recent
opponent is deferred for up to 15 seconds while compatible alternatives are sought;
explicit joins and private, bot, ranked, tournament, and manual rooms retain their
existing admission flow. This adds no PostgreSQL table or migration.

Casual-series continuation records in presence/Redis retain the optional
`allowRollback` setting; this introduces no PostgreSQL table or migration.

Player replay files live in the player's Google Drive; `account_replays` stores
their index and sharing metadata. Migration 041 rebuilds the metadata table transactionally, preserving existing entries while allowing neutral spectator seat -1 and friends visibility. Friends-only sharing keeps a protected server copy in `friend_replay_files`: replay UUID primary key and cascading foreign key, owner account foreign key, gzip archive stored as `bytea`, compressed byte size, and creation time. The owner index supports a 128 MiB compressed-byte quota per account, serialized through the account row lock. Files are at most 32 MiB, are removed when sharing is revoked or the replay is deleted, and are never exposed through a public Drive permission. Every download checks current friendship and blocks. Neutral spectator files omit private zones and respect identity privacy.

Migration 053 adds public replay listing columns to `account_replays`: nullable `format` (the room's deck format), nullable `player0_account_id` and `player1_account_id` (seated accounts, no foreign key; null means a bot or guest seat), `identities_recorded` (false for rows indexed before the migration), and nullable `published_at`. Setting a replay to public stamps `published_at`; any other visibility, or attaching a different Drive file, clears it. Partial indexes `account_replays_public` `(saved_at DESC, id DESC)` and `account_replays_public_format` `(format, saved_at DESC, id DESC)`, both `WHERE published_at IS NOT NULL`, serve `GET /replays/public`. The listing returns only public, saved rows with recorded identities. It excludes a row when a non-owner seat's account currently hides its identity from spectators or no longer exists, and when the viewer and owner block each other. Replays indexed before migration 053 have no recorded seats, so they stay link-only even when shared again. The listing is empty while the server has no Drive API key.

Migration 041 also adds `direct_messages` with UUID primary key, cascading sender and recipient account foreign keys, bounded body, creation time, and nullable read time. Sender/recipient pair indexes order history by creation time and UUID; a creation-time index supports retention. History is limited to 50 messages per page. Reads and writes require a current friendship and no block in either direction; message sends serialize on account locks to enforce the shared chat cooldown across processes. Messages expire after 30 days and the startup/15-minute cleanup job deletes expired rows. Recipient reports preserve only the selected message evidence in the existing private feedback moderation inbox, without a GitHub mirror; that moderation evidence follows feedback retention rather than chat retention.

The account preferences include `spectatorAccess` (`everyone` by default, `friends`, or `nobody`) and `shareProfileStats` (false by default). The API enforces both players' spectator policies, including existing spectators and reconnects. Friends/nobody games stay off public listings. Explicit `shareProfileStats` consent controls friend detail statistics independently of the existing device-synchronized `profileStats` display preference. Report replays store the private action record
in PostgreSQL. Local replay reproduction files under ignored `replays/` contain
decklists and actions; committed regressions use trimmed fixtures.

The account JSON preferences include optional boolean `shareDeckAfterMatch`. Missing values enable post-match deck-list sharing. The room checks the deck owner’s stored preference before sending the initial list to a seated opponent after game over; this setting does not change existing board review or replay exports.

The account JSON preferences also include optional boolean `listLiveMatches`. A missing value means on; an explicit `false` remains an opt-out. When neither seated account in a casual room has opted out, the room adds a `live` entry to its Colyseus matchmaking metadata (in presence/Redis when configured). The entry holds the spectator code, display names, format, start time and spectator count, and the room removes it at game over. The web client never copies this preference from device storage, because public listing is an account preference. This introduces no PostgreSQL table or migration.

The account JSON preferences include optional boolean `hideIdentityFromSpectators` (default false). Rooms capture it before admitting spectators for each game. It withholds that player’s nickname, avatar and session identifier from spectator state and uses an empty name in public listings, rendered as a numbered player label. Participants retain both identities. The spectator roster is transient room state visible only to participants; authenticated names come from single-use account room tickets, and guests contribute only to a count. No PostgreSQL migration is required.

The account JSON preferences include optional `cardImageLanguage` (`en`, `ja`, `ko`, or `zh`). It selects default images for the collection and new deck copies. Explicit per-copy artwork remains stored in the deck. Existing decks change only through the bulk apply action. No PostgreSQL migration is required.

## Deck providers

Migration `037-deck-providers` adds three provider-owned tables:

| Table                     | Purpose                                                                                                       | Retention                                                                     |
| ------------------------- | ------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| `deck_provider_cache`     | Shared response JSON, expiry, request budget and upstream cooldown; primary key `key`                         | Response freshness 15 minutes; expired entries cleaned on successful requests |
| `deck_provider_snapshots` | Weekly extracted JSON keyed by provider and request path, with collection timestamp                           | Latest successful snapshot per key; retained across failed refreshes          |
| `deck_provider_sync_runs` | Weekly execution period, attempt/completion timestamps and collection count; primary key `(provider, period)` | 90 days                                                                       |

The API never persists provider API keys. PostgreSQL advisory locks coordinate cache fills and weekly collection across API processes.

### story_battle_completions

Account-scoped solo story victories. Primary key `(account_id, battle_id)`; `account_id` references `accounts(id)` with cascade deletion. Stores the authoritative `match_id` and `completed_at` timestamp. Only the game room records a victory; HTTP exposes read-only progress. No chapter text or hidden combat state is stored here. `battle_id` also holds tutorial lesson IDs, which start with `tutorial-`.

### story_guest_completions

Anonymous story victories keyed by a SHA-256 hash of a random browser token and battle ID. Stores match ID and completion time. Only authoritative match wins write this table. Guest progress is separate from account progress; clearing browser storage loses access to it. `battle_id` also holds tutorial lesson IDs, which start with `tutorial-`.

Manual turn scaffolding automatically unsuspends the incoming player, draws once after the initial first-player skip, and projects `manual.canHatch` / `manual.canMoveFromBreeding` during the exclusive hatch/move/skip window. `manual.turnPhase` tracks this guided flow while the engine command router remains in Main; scheduled empty-deck draws end the game through the normal result lifecycle. Card effects remain manual. Manual synchronized state additionally records simultaneous permanent `manualStatuses`, public effect and target signals, restart proposal seats and restart count. Consensual restarts retain staged decks and seats, derive fresh deterministic setup identities, and reoffer mulligans; private inspection data is cleared. Manual reveal gallery entries may include their public source zone and instance ID for owner-authorized movement. Manual replay summaries may use mode `manual`. Input-record rules include optional `gameMode`; missing values retain automatic execution. Manual games do not write `match_records` or `account_recent_matches`. Private inspection projections are stripped from player replay frames and never enter shared replay metadata. No SQL migration is required for these JSON fields.

Manual replay JSON may also contain visual turn/combat stages, batch revelation identities, token instances and structured permanent modifiers (Security Attack, keywords and colors). These fields use schema defaults when loading older replays. Undo restores these projections; private consultation data remains excluded. No SQL migration is required.

### Ephemeral social state

The Colyseus cluster presence owns the social keys. LocalPresence is used for a single process and RedisPresence for replicas. No game state is stored here.

| Key                                       | Lifetime and purpose                                                                               |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `social:presence:<accountId>`             | Index of connection leases; refreshed with a 60-second expiry                                      |
| `social:lease:<accountId>:<connectionId>` | 45-second expiring online/lobby/match lease, renewed every 10 seconds                              |
| `social:account:<accountId>`              | Pub/sub channel for friends, presence, notifications and invites                                   |
| `social:invite:<id>`                      | Invite data retained for 120 seconds; valid for 60 seconds and only while its host room is waiting |
| `social:invites:<accountId>`              | Pending invite index; expired entries are pruned when reading                                      |
| `social:invite-answer:<id>`               | Atomic first-answer claim, expiring after 120 seconds                                              |

All presence and invite access is authenticated and restricted to current friends without blocks in either direction. Multiple connections keep independent leases.

The account JSON preferences include optional boolean `groupIdenticalTamers` (default true). It controls client presentation of identical Tamers in the organized field and synchronizes with device storage. It does not change authoritative permanent references or game state. No PostgreSQL migration is required.

Completed replay files can include optional consent-filtered deck snapshots. Replay index summary JSON and new Drive file metadata retain only the corresponding deck cover card IDs, never full deck lists. Older replay files and index summaries omit this metadata and remain valid. Participant files include the owner’s own deck; opponent decks require post-match sharing, and spectator files also honor hidden identities.

Deck history migration 042 adds `saved_decks.cards_changed_at` (milliseconds, initially zero for existing decks). Saving a different card multiset or format advances it; names, card order and cosmetics do not. New history JSON includes private `ownDeckId`, `ownDeckName`, `ownDeckKey` and `ownDeckStartedAt` fields. These stay server side; the history response exposes the participant’s own deck name as `deckName`. Deck statistics use durable human results from `account_deck_matches`, ignore the result filter, and honor mode/opponent filters. Current-list statistics require a matching composition and a deck selection time at or after the latest card change. The optional `deckWindow=last100` query limits the deck total and each deck's comparison record to that deck's newest 100 matching ledger rows; current-list statistics ignore it. Older records without deck metadata remain unattributed.

`account_deck_matches` (migration 042) retains one result per `(account_id, room_id)`, with deck ID, deck name and minimal JSON (mode, opponent name/kind, outcome, finish time, composition key and deck selection time). It has an account FK with cascading deletion and an `(account_id, deck_id)` index. It is independent of recent-history and replay deletion. Its JSON excludes full opponent decks; it retains the opponent owner account ID privately to recheck current sharing preferences. A competitive placeholder is enriched by the room writer once its deck selection time is known. Unknown pre-feature matches are not backfilled.

Finished history records can also retain private `ownDeck` snapshots (starting cards, artwork, format and name). The participant-only `GET /account/matches/:id/own-deck` serves that frozen list and strips its local deck ID. Earlier tracked records can reconstruct cards and format from `ownDeckKey`; they have no artwork snapshot. List responses expose only `hasOwnDeck`, never the snapshot or composition key. Opponent snapshot reads keep honoring current sharing preferences.

Migration 043 indexes `account_deck_matches.record.ownDeckSignature`. New ledger JSON carries SHA-256 composition signatures for both decks, the opponent deck name for participant-only matchup labels, a representative public card ID, and the private opponent owner ID. Matchup analysis is currently deferred: history requests do not compute or return these aggregates. Existing metadata and the applied index are retained.

Migration 049 removes `ownDeckKey` from `account_deck_matches.record`; it held the full sorted card list and was about 56% of each row. Current-list statistics compare `ownDeckSignature` instead, which the 043 index covers. The full key stays in `account_recent_matches.record`, where older records still rebuild their frozen deck from it.
